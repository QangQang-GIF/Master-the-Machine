# MTM root

Player owns this single Codex session. Use only native subagents for match workers; never launch nested Codex/other agent CLIs. In production, skills/profiles are frozen. Use current descriptor values, approved origins and assigned workspace only; never log/persist credentials, inspect hidden tests/tasks, or access another team's data. On host approval blocks report `HOST_APPROVAL_REQUIRED` with the exact reason and preserve progress.

For PREPARE/RESUME, follow `game-preparation`/`team-recovery`. For `START_GAME`, call `configure_session(descriptor)`, `login_match()` as needed, then `refresh_match()`. Use native MCP or the same persistent `runner.control` stdio bridge described in preparation; keep its session alive across phases. Missing MCP discovery does not mean contest APIs are unavailable. Both transports use identical deterministic guards, journal and progress logger. Never handwrite unvalidated status or fabricate readiness. Append validated events to the exact progress log with business keys.

## Credit discipline (every Root call re-reads the whole context)
- One tool call per decision. Never read or write worker files with the shell: `record_worker_result(key)` reads `worker_result.json` itself and stops the worker's server; `integrate_and_submit(key)` cherry-picks, validates, pushes and submits; never build payloads or run `git cherry-pick`/`push` yourself unless `integrate_and_submit` returned CONFLICT.
- Never fetch KB/logs/fixtures for a worker or copy them into its folder. Workers call `call_company_tool`, `collect_logs` and `fetch_fixture` themselves (the helper serves them through the Root process); KB articles named in the brief are prefetched into the envelope.
- Never read the pack's source, skills or handoff files during the match; the tool descriptions are the contract.
- Keep progress messages to one short line. Do not re-check what a tool already verified.

## Scheduling loop

1. Refresh the public match projection throughout play; new items can appear at any time. Trust server status/time, including pause-adjusted deadlines. Discover all visible items and report status. Continue until FINISHED, even when the current queue is empty.
2. **Capacity and order come from `plan_tasks()`** (one `priority_key()` for dispatch, the ready queue and the PI-first gate):
   - Capacity is the effective config printed at start (`max_workers` / `normal_workers` / `pi_burst_slots`); PI burst slots are extra slots only a PI may use. Never assume a fixed number of workers.
   - **Two flows only: ordinary items and PI.** Every ordinary item is treated alike (no ranking by type, points or size); all workers use the same model (`MTM_WORKER_MODEL` / `MTM_WORKER_EFFORT`) and the same `agent_profile`. PI burst slots are extra slots only a PI may use.
   - Order: a ready item whose deadline is inside its critical window and still has `submitBudgetSeconds`, then PI, then every other item by least time left. Take `selected` and `readyToIntegrate` in the order returned; do not re-sort.
   - `claim_task` returns `taskEnvelope.lane` (`pi` or `normal`), `model`, `reasoning_effort` and `agent_profile`; spawn with exactly those.
   - Wait only with `wait_for_update(timeoutMs=55000, sinceEventId)`. Call `plan_tasks()` only after an event that can change capacity or readiness (new items, result recorded, item submitted/closed). It returns early on new items, PAUSED/FINISHED and native events (worker result available/recorded, `DEADLINE_FLUSH_REQUESTED`, `FLUSH_TIMEOUT`, `RECONCILIATION_REQUIRED`); pass back its `eventCursor`.
3. For each selected OPEN item, call `start_work(backlogItemKey)` and retain its exact template/MVS. The helper resolves only that item's publicly announced paths, including post-clone documents; never scan or checkout other tasks. `unavailableAnnouncedFiles` reports a declared path absent from the assigned branch without inventing its content. If official MVS/checkers and the task brief provide sufficient requirements, proceed from those; otherwise report the precise missing input. Then `claim_task(backlogItemKey, workerId, estimatedSeconds)` returns ownership/worktree and TaskEnvelope. Spawn the selected native worker with `fork_turns="none"`, the compact `taskEnvelope` exactly as `claim_task` returned it (its `full_envelope_path` points to the full envelope the worker reads first), owned paths/result location and needed skills. `start_work`, `claim_task` and `plan_tasks` return compact summaries and save the full payload under `state/<match>/handoff/`; do not read or paste those files into your own context. Never forward credentials. Source/answers use `worktreeRoot/repository.folder`; preserve the Git prefix and isolate test resources.
4. Workers investigate, implement, verify, and return WorkerResult; they do not push or call Submit. Root calls `record_worker_result(backlogItemKey)` (no workerResult argument) as soon as a worker finishes or `workerResultsAvailable` lists it; the helper reads the file, fixes lossless type slips, stops the worker's server and returns the decision. If it reports a contract problem, relay that exact line to the still-running worker once; do not edit its file. Failing tests stay in `test_results` with `passed=false`; never move them elsewhere to obtain DONE or VERIFIED. `VERIFIED` means the MVS really passed.
   - **One order after every result, set by the policy:** if any `readyToIntegrate` item has `decision.mustFinalize`, integrate it first; otherwise dispatch `plan_tasks().selected` (start_work, claim_task, spawn) and then integrate `readyToIntegrate[0]`.
   - **Follow `decide(backlogItemKey)`** (also returned by `record_worker_result` and attached to each ready item): `SUBMIT` → `integrate_and_submit(backlogItemKey)`; `CONTINUE_WORK` → leave the running worker alone (if `mustFinalize`, ask it to commit and write its final result now); `REWORK` → `reconcile_worker(requeue=true)` (bounded retries; the new envelope lists `prior_attempts` for hand-off); `HOLD_FOR_REVIEW` → automatic review window, then call `decide` again; `CLOSE` → record the reason and move on.
   - **`deadlineFlushRequests`**: tell that worker to commit and write its final `worker_result.json` immediately. The coordinator never converts a running worker into a result. Only if the worker has confirmed it stopped and its own `submit.json` is an honest PARTIAL may you call `flush_snapshot(...)`; the policy still decides whether it is submitted.
   - For `overdueWorkers`, first read and record any final result that exists; otherwise checkpoint/interrupt with native tools, confirm the worker stopped, then call `reconcile_worker`. A result arriving after its item closed or from a fenced attempt is kept for audit only.
   - A worker's budget ends at its real hand-off point: 150 s before the item's deadline, or 240 s before the match ends. A hand-off leaves no time for a new attempt; the policy accounts for that (`REWORK` needs `submitBudgetSeconds` + `MTM_MIN_REWORK_SECONDS` left).
   - **Submit results that pass.** A `SUBMIT` decision is acted on immediately; never send a passing result back to polish or re-capture evidence (594OYFBS lost CR-01, 140 points, this way).

## Submit revision and company tools (I5NLYST2 lessons)
- `integrate_and_submit` submits the root checkout HEAD pushed to the assigned branch after integrating the worker commits (a new SHA, never the worker's). It returns `ACCEPTED` + receiptId, or `CONFLICT` with files (lock released): then follow `decide` (REWORK via `reconcile_worker(requeue=true)`), or resolve by hand and call it again.
- Company tools (`kb_search`, `search_logs`, `get_test_data`, `collect_logs`, `fetch_fixture`) go only through the MCP helper, which retries transient timeouts itself. If one still fails, report the exact error text in a blocker and continue other items; never write your own HTTP/bearer bridge or retry loops (automatic review rejects them).

## Until the end

- Keep calling `wait_for_update`/`plan_tasks` until the match is FINISHED. Never end your turn while the match is running.

## Integration and submission

**STRICT ROLE BOUNDARY & SUBMISSION (Root Orchestrator)**:
- **No idle queues**: an item whose decision is `SUBMIT` is integrated and submitted without waiting for other items. Valid is not the same as worth submitting: an item is submitted only on `SUBMIT`.
- **Honest status**: DONE needs every MVS PASS (fail closed, never downgraded silently). An honest PARTIAL of any ordinary item is submitted at the latest useful moment (when `decide` says SUBMIT); a PI PARTIAL only when `MTM_PI_PARTIAL_SUBMIT=1`. BLOCKED is never submitted.
- **Immediate Remediation on Submission Feedback**: If `submit_work` or Game Master returns ANY error (e.g. missing evidence file, schema mismatch, or parity error), DO NOT abandon the task. Classify the error first: a validation rejection (400/422) leaves the item open, so correct the real problem (re-run the missing check or fix the payload from real data, never fabricate evidence or test results), commit, and resubmit once. A closed/expired/not-found answer (409 closed, 404, 410) is terminal: do not retry. A timeout, 5xx or 429 has an unknown outcome: do not resubmit blindly, reconcile against the server record first.
- **Mandatory Submission Before Slot Reassignment**: An item MUST be successfully submitted (server receipt received) before reassigning that worker or releasing the item.
- The Orchestrator integrates with `integrate_and_submit(key)`: lock -> cherry-pick -> deterministic guards on submit.json & evidence (fail closed; no silent downgrade of status or invented evidence) -> rebase/push -> journaled Submit -> receipt.
- The integration lock is a lease (8 s) renewed by a heartbeat while `submit_work` is running; a dead holder stops renewing and the lock is reclaimed. A Submit whose outcome is unknown never releases the lock on a timer: after 120 s the item is `RECONCILIATION_REQUIRED`; call `integrate_and_submit` (or `submit_work`) for that item again and it replays the journaled body with the same idempotency key (bounded attempts, then the item is parked for review). Git commit/rebase/push failures stop the submit with their real cause.

Serialize integration/push/Submit; workers continue independent work. Prioritize urgent ready items. `integrate_and_submit` acquires the integration lock itself (use `integration_gate(backlogItemKey, action="begin")` only for a manual conflict resolution). The root alone holds this lock through verification, push, and Submit. On failure, do not abandon: resolve missing files from real work, reconcile Git/push state, and re-submit only when the error class allows it; successful `submit_work` releases it on the real receipt. Verify the patch is confined to permitted paths, integrate into the assigned branch, resolve conflicts. Source, answers, and evidence stay under `matchRoot = checkoutRoot/repository.folder`.

For every item, cover all required acceptance/MVS scenarios and exact evidence requirements, including requested before-change captures. All declared evidence files MUST exist as nonempty files in `answers/<key>/evidence/`. If browser capture times out or cannot settle, capture a diagnostic screenshot of the current app or write a diagnostic report; NEVER omit required evidence files from the commit.

Fill `answers/<key>/submit.json` exactly from the received template. Before dispatch, deterministic guards verify answer/payload parity, complete passing required results, nonempty contained evidence in the exact commit tree, permitted diff, full SHA, assigned branch, ordinary push, and remote ref parity. Never force-push or alter immutable/secret/agent files.

As soon as the decision is SUBMIT, call `integrate_and_submit(backlogItemKey)` immediately without waiting for other items (low-level `submit_work(backlogItemKey)` reads the answer, revision and journaled id from disk; never paste the answer). Preserve the journal's canonical request bytes and idempotency identity across uncertainty; reconcile rather than submit a second solution. Record a real server receipt; ACCEPTED is not graded PASSED. Track grading and all item outcomes. A solved item left unsubmitted is unfinished work.

On PAUSED, halt new work/submission dispatches and honor Player controls; on FINISHED stop descendants and finalize logs. CLOSED items are terminal; record and advance without retry loops. Keep unresolved blockers visible while other eligible tasks continue.
