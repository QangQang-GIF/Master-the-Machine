# MTM root

Player owns this single Codex session. Use only native subagents for match workers; never launch nested Codex/other agent CLIs. In production, skills/profiles are frozen. Use current descriptor values, approved origins and assigned workspace only; never log/persist credentials, inspect hidden tests/tasks, or access another team's data. On host approval blocks report `HOST_APPROVAL_REQUIRED` with the exact reason and preserve progress.

For PREPARE/RESUME, follow `game-preparation`/`team-recovery`. For `START_GAME`, call `configure_session(descriptor)`, `login_match()` as needed, then `refresh_match()`. Use native MCP or the same persistent `runner.control` stdio bridge described in preparation; keep its session alive across phases. Missing MCP discovery does not mean contest APIs are unavailable. Both transports use identical deterministic guards, journal and progress logger. Never handwrite unvalidated status or fabricate readiness. Append validated events to the exact progress log with business keys.

## Credit discipline (every Root call re-reads the whole context)
- One tool call per decision. Never read or write worker files with the shell: `record_worker_result(key)` reads `worker_result.json` itself; `integrate_and_submit(key)` locks, cherry-picks the worker commits, pushes and submits. Use manual Git only when it returns CONFLICT.
- Never fetch KB/logs/fixtures for a worker or copy them into its folder: workers call `call_company_tool`, `call_company_tools`, `collect_logs` and `fetch_fixture` themselves (the helper serves them through the Root process). KB articles named in the brief are prefetched.
- `dispatch_tasks`, `start_work`, `claim_task`, `plan_tasks` and `refresh_match` return compact summaries and save the full payload under `state/<match>/handoff/`; do not read those files. Spawn workers with the compact `taskEnvelope` as returned (its `full_envelope_path` is read by the worker).
- Never read the pack's source, skills or handoff files during the match. Keep progress messages to one short line.

## Scheduling loop

1. Refresh the public match projection throughout play; new items can appear at any time. Trust server status/time, including pause-adjusted deadlines. Discover all visible items and report status. Continue until FINISHED, even when the current queue is empty.
2. **Lanes (`plan_tasks()`)**: `laneSlotsFree` has `normal` (any item), `deadline` (items with a deadline) and `pi` (Product Incidents), e.g. 3/3/3; a deadline item or PI overflows into a free normal slot (`laneSlot` says which); ordinary items never use the deadline or PI lanes. Never assume a number; dispatch exactly what `selected` lists, in its order (deadline-imminent, PI, earliest deadline, then the rest). Every worker uses the model and effort the claim returns.
3. **Dispatch in one call**: `dispatch_tasks(items=[{backlogItemKey, workerId}, ...])` for all `selected` items: Start Work runs in parallel and each entry returns the compact claim summary. Spawn one native worker per entry with `fork_turns="none"` and that `taskEnvelope` as-is (its `full_envelope_path` is read by the worker). Never forward credentials. Use `start_work` + `claim_task` only for a single retry of an entry that returned an error. **Every announced item is workable**: odd inputs (another item's file such as `challenge/CR-05-seed.js`, binaries, subfolders) are accepted; `unavailableAnnouncedFiles` / `announcedInputWarnings` / the envelope's `input_warnings` only report files that were skipped or absent, so dispatch and work the item anyway from the brief/MVS. If Start Work succeeded but the claim failed, call `claim_task(key, workerId)` once. Never repeat an identical failing call: after one retry, record `report_progress({"type": "BLOCKER_OPENED", "blockerId": "<key>-<short reason>", "backlogId": "<key>", "summary": "<exact error>"})` and continue with other items.
4. **Waiting**: only `wait_for_update(timeoutMs=55000)`. It returns at once on a new item, a match state change, `workerResultsAvailable`, `deadlineFlushed`, `readyToIntegrate` or `dispatchable` (free slot: `dispatch_tasks` those keys); act on exactly what it names. With nothing running or ready it may wait up to ~240 s: keep calling it until FINISHED (new items can still appear). While idle, call it again without writing a progress message.
5. **Workers stay on their own item**: do not relay messages between workers. When a brief says an item needs another item's fix (CR-07 needed BUG-11's), integrate and submit the prerequisite as soon as it is ready; the dependent worker rebases onto the root branch.
6. **Worker finished** (`workerResultsAvailable` or the worker's own message): `record_worker_result(key)` (no workerResult argument), then `integrate_and_submit(key)` at once, then `plan_tasks()` + `dispatch_tasks` for freed slots. If `record_worker_result` reports a contract problem, relay that exact line to the worker once; do not edit its file. A result that is already ready (`note`) goes straight to `integrate_and_submit`.

## Deadlines (items with `deadlineMinutes`; the clock runs from the item's RELEASE, not from Start Work)
- A deadline item is worth nothing once the Game Master closes it. Dispatch it the moment it is selected; never queue it behind a running integration you could finish later.
- When `plan_tasks`/`wait_for_update` reports `deadlineFlushed` (about 2.5 min before an item deadline, 4 min before the match end), the helper has already committed the worker's `answers/<key>` and marked its last commit ready: call `integrate_and_submit(key)` immediately (before anything else), then interrupt that worker. Do not call `record_worker_result` for a flushed item unless the worker has finished after the flush.
- For `overdueWorkers`, checkpoint/interrupt with native tools, confirm the worker stopped, then call `reconcile_worker` before retry/reassignment. Never release a live worker's capacity or discard artifacts.

## Integration and submission

**STRICT ROLE BOUNDARY & IMMEDIATE SUBMISSION (Root Orchestrator)**:
- **No Idle Queues**: Con nào làm xong là phải nộp liền! As soon as a worker returns a result, immediately integrate and submit. Never let a completed worker wait in an integration queue while deadlines expire.
- **`SUBMIT_SCHEMA_INVALID`** (local check against `challenge/<key>-submit.schema.json`; nothing was sent): the grader would score the whole item 0. If the worker is still running, relay the listed fields to it once; otherwise fill them with real values from the item's evidence in the root checkout, commit, and call `integrate_and_submit(key)` again. With under ~6 min left call `integrate_and_submit(key, schemaAutofill=true)` (near the deadline the helper does this itself).
- **Submission errors**: 400/422 (missing evidence, schema, parity) keep the item open: fix exactly what the error names with real data (capture the missing evidence, correct `submit.json`), commit it in the root checkout and call `integrate_and_submit` again, once. 404/410 or 409 closed/expired: the item is closed, move on. Timeout/5xx/429: fix nothing; call `integrate_and_submit` again: it first checks the board (a timed-out request has often arrived; the receipt is then recorded) and otherwise resends the journaled request, even after the deadline (the Game Master decides). Never push or call `submit_work` by hand for an item `integrate_and_submit` can handle.
- **After the last item is submitted**: do not refresh, read files or tidy worktrees; only `wait_for_update` until FINISHED or a new item.
- **Mandatory Submission Before Slot Reassignment**: An item MUST be successfully submitted (server receipt received) before reassigning that worker or releasing the item.
- The Orchestrator integrates with one call, `integrate_and_submit(backlogItemKey)`: lock -> cherry-pick -> guards on submit.json & evidence -> push -> journaled `submit_work` -> receipt. An unknown-outcome submit (timeout/5xx) is resent with the same journaled body inside that call; if it still fails, call it again (never build a new submission).

Serialize integration/push/Submit; workers continue independent work. Prioritize urgent ready items. `integrate_and_submit` takes the integration lock itself; never call `integration_gate` before it (use it only to resolve a CONFLICT by hand). The root alone holds this lock through verification, push, and Submit. On failure, do not abandon: resolve missing files, auto-heal evidence, reconcile Git/push state, and re-submit; successful `submit_work` releases it on the real receipt. Verify the patch is confined to permitted paths, integrate into the assigned branch, resolve conflicts. Source, answers, and evidence stay under `matchRoot = checkoutRoot/repository.folder`.

For every item, cover all required acceptance/MVS scenarios and exact evidence requirements, including requested before-change captures. All declared evidence files MUST exist as nonempty files in `answers/<key>/evidence/`. If browser capture times out or cannot settle, capture a diagnostic screenshot of the current app or write a diagnostic report; NEVER omit required evidence files from the commit.

Fill `answers/<key>/submit.json` exactly from the received template. Before dispatch, deterministic guards verify answer/payload parity, complete passing required results, nonempty contained evidence in the exact commit tree, permitted diff, full SHA, assigned branch, ordinary push, and remote ref parity. Never force-push or alter immutable/secret/agent files.

As soon as the worker result is recorded, call `integrate_and_submit(backlogItemKey)` immediately without waiting for other items (low-level `submit_work(backlogItemKey)` reads answer, revision and journaled id from disk; never paste the answer). Preserve the journal's canonical request bytes and idempotency identity across uncertainty; reconcile rather than submit a second solution. Record a real server receipt; ACCEPTED is not graded PASSED. Track grading and all item outcomes. A solved item left unsubmitted is unfinished work.

On PAUSED, halt new work/submission dispatches and honor Player controls; on FINISHED stop descendants and finalize logs. CLOSED items are terminal; record and advance without retry loops. Keep unresolved blockers visible while other eligible tasks continue.
